# rvnd-govern - reference

## What it drives — the RVND server, never a local engine

This skill holds no governance logic. It sequences calls to the RVND governance MCP server (the
action gate, `governance_lane_list`, `governance_map`, `officer` preview, `governance_lane_register`)
and renders their results. If the server is absent or its governance layer is off, the skill fails
closed — it does not fabricate a verdict.

## Identity first — the no-id wall

Before step 3, resolve three identities the server recognises: the **agent** (a registered agent
with a lane, not "the assistant"), the **folder scope**, and the **acting person** for any step
that needs confirmation. An unresolved principal stops the flow there. Never invent or reuse an
identity to continue. A folder with no policy is ungoverned and therefore fail-closed for
consequential acts — register or resolve it first.

## The proposal envelope — typed, not a sentence

A proposal is the typed object in `../../schemas/proposal.schema.json`. The skill assembles the
parts it owns and asks RVND to generate and validate the Loomground meaning; it never writes `.lg`
and assumes it correct.

- **intent** — the source grounding: the user's exact words/selection, the acting actor, the host
  (chat / cli / sheet), the context.
- **scope** — the object grounding: the stable `boundary_id` and members (RVND/Versum identities,
  not display names), and whether membership is static or dynamic.
- **runtime_bindings** — Loomground roles/kinds bound to RVND parties/actors and capabilities
  (e.g. `accountable-publisher -> party:maria`, `external-publication -> capability:publish`).
- **loomground.constructs** — generated by RVND, restricted to the real vocabulary
  (`../../references/vocabulary.md`): the node classes, cords, and declarations only. The skill
  presents these; it does not author them.
- **residual** — everything the user meant that no real construct expresses (see below).
- **validation** — the server's result: well-formedness, the conformance vector set, the
  **canonical observation**, a verdict preview, warnings. Presented, never computed by the skill.
- **evidence** and **versions** — the evidence grounding (Versum span/claim + legal source from
  the language's `grounding.json`) and the version grounding.

The server checks every constrained dimension against the lane. Missing scope, an unapproved
action or footprint, a connector change, a policy change, or a grade increase each produce a
denial.

## The residual ledger

Meaning that no current Loomground construct expresses does not get approximated — it goes in
`residual`, visibly unresolved, with a reason and the clarification the skill may ask. "Use the
files responsibly", "make it culturally appropriate": neither is a `kind`, a guard condition, an
evidence requirement, a role, or a decision criterion. There is a hard reason a phrase like this
cannot be smuggled into a `when <guard>`: a guard ranges only over `{kind, risk, party, tags}` with
`{=, >=, contains}` and never computes. So it stays residual until a person defines it as a real
construct. The skill may ask whether it should become a human `reservation`, whether there is a
policy source, who is competent to decide, or whether it prohibits release or only requires
evidence (an `egress-obligation`). It must not invent a `prohibition` or an approval rule.

## Tightening vs loosening

Decide the direction before you render anything:

- **Tightening** (a lower grade, fewer classes, a narrower footprint, sealing the folder) is the
  safe direction. Preview it through the officer preview so the shown effect is the server's, then
  apply. Records who tightened and why.
- **Loosening** (a higher grade, more classes, a new connector, opening a sealed folder, a more
  permissive policy) is dangerous. It **always** needs a new versioned lane, a named approver, and
  a written rationale, and it is fail-closed until it has them. Never loosen implicitly or by
  reusing a prior approval for a different scope.

## What it returns

The server's verdict (allow / hold / deny) as a discrete lamp, the rule that produced it, and —
once applied — the signed receipt. Nothing is asserted without its rule and key. A held or denied
action is rendered as held or denied, never softened.

## Guardrails

- The server decides; this skill renders. No host-side verdict, ever.
- Orchestrate, never invent: assemble the envelope from real `workspace_*` op results; any field the
  server cannot supply goes in `validation.unavailable_fields` and the proposal stays unapplied. Do
  not fabricate a construct, validation, binding, evidence, or observation.
- Fail-closed on every write path: missing step, unreachable server, unresolved principal → stop.
- Requested is not granted. Status words stay "requested / pending / proposed" until the receipt.
- Attributed, not asserted — every outcome carries rule, key, and (for loosening) approver.

## Pairing

The entry point for the plugin. `rvnd-decide` owns the human confirm step in depth; `rvnd-audit`
verifies the receipts this skill produces; `rvnd-incident` handles the stop/revoke/transfer path
when something goes wrong; `rvnd-build-surface` composes the cards this cycle renders.
